MOHANO-SERVER 시작 문서
=======================

상태: 익명 사용자·Google/Apple 계정 identity·refresh JWT session·프로필과 기본 후보는 MySQL
repository로 영속화했다. 매칭 조건·통화·채팅 API는 아직 더미 메모리 저장소로 동작한다.

목표
----
`MOHANO-SERVER`는 MOHANO의 인증, 프로필, 매칭, 채팅, 통화 신청을 위한 단일 API
기준이다. Flutter 앱과 분리해 운영하며, 사용자의 데이터와 권한을 안전하게 관리한다.

확정한 결정
------------
- FastAPI와 MySQL을 사용한다.
- API는 HTTPS JSON REST이며 `/v1`으로 버전 관리한다.
- 인증은 LINE, Google, Apple OAuth credential과 Kakao access token을 서버에서 검증한 뒤 발급하는 JWT를 쓴다.
- access JWT는 짧게 유지하고 refresh JWT는 회전·폐기한다. refresh JWT 원문은 저장하지 않는다.
- Redis는 초기 범위에 넣지 않는다.
- 채팅은 실시간 연결 없이 REST로 저장하고, 화면 진입 또는 사용자 새로고침 시 조회한다.
- 음성 미디어는 WebRTC P2P로 이용자끼리 직접 전송한다. 서버는 미디어 relay를 하지 않는다.
- 서버는 통화 신청과 연결 전의 짧게 만료되는 SDP·ICE signaling 데이터만 REST polling으로 전달한다.
  WebRTC 연결 뒤의 정상 종료 알림은 P2P Data Channel으로 직접 전달하고, server는 종료 상태 기록과
  예외적인 연결 단절에서의 단발성 session 확인만 처리한다.
- 로컬 개발용 MySQL과 Silo(MinIO 호환) Docker 구성을 `etc/infra`에 둔다. 사진 object storage는
  로컬에서 Silo, 운영에서 Cloudflare R2를 사용하되 S3 호환 API 계약을 유지한다. 운영 API·DB는
  Cloud Run(FastAPI 컨테이너)과 Cloud SQL(MySQL)을 사용하고, Terraform은 리소스 정의까지만
  제공한다. 실제 `terraform apply`, R2 secret version 입력, migration 실행, R2/DNS/OAuth portal 변경은
  운영자 확인 뒤 수행한다.

남은 작업 순서
----------------
아래 순서는 Flutter 앱의 `MOHANO-APP/etc/design/00-start.txt`와 동기화한다. 각 단계의 완료
조건을 확인하기 전에는 다음 단계로 넘어가지 않는다.

01. Google·Apple·LINE·Kakao 인증·세션 안정화 (진행 중)
- Google·Apple ID token 교환, 신규/기존 계정, 온보딩 중단 계정, refresh token 회전을 실기기에서 확인한다.
- Apple은 JWKS ID token 검증과 Android callback을 구현했다. Apple Developer Program의 Service ID,
  외부 HTTPS Return URL, 실제 기기 검증과 authorization code 기반 철회 확인은 남아 있다.
- `needs_onboarding`은 identity 존재 여부가 아니라 `profiles.onboarding_completed`로 계산한다.
- 401/403과 provider 검증 실패는 JSON 오류 계약으로 반환하고 credential·JWT는 로그에 남기지 않는다.
- 로그아웃 API와 refresh session 폐기는 앱 설정 메뉴에 연결했다. 실제 기기에서 폐기 동작을 확인한다.

02. Profile·사진 영속화 (완료)
- MySQL Profile API와 Flutter 편집 화면의 텍스트 필드는 동기화했고, API 입력 검증도 적용했다.
- 이벤트 시각은 서버 UTC가 기준이며, 앱이 수집한 IANA 시간대는 비공개 프로필 값으로 저장한다.
- 사진의 바이너리는 DB에 저장하지 않는다. private S3 호환 storage의 signed upload/download URL을
  사용하며, 서버에는 object key·순서·대표 여부만 저장한다. 실제 기기 업로드·삭제·재실행 후
  표시를 확인한다.
- 사진은 별도 사전 검수 없이 업로드 완료 직후 프로필에 반영하고 상대에게 즉시 노출한다.
- 계정 삭제는 논리 삭제 사용자 행만 남기고 저장 데이터·사진·연결 identity·세션을 지우도록 구현했다.
  프로필 공개 정책은 별도로 확정한다.

03. Matching MySQL 전환 (진행 중)
- `MatchingService`의 조건 저장과 후보 조회는 MySQL repository로 전환했다. 완료한 프로필과
  정상 계정은 알림 권한·FCM token·foreground 상태와 무관하게 후보로 조회하고, 본인·탈퇴·온보딩
  미완료 사용자는 제외한다. 최근 foreground 상태와 유효한 통화 알림 token은 같은 노출 이력 안에서
  응답 가능성이 높은 사용자를 우선 정렬하는 기준일 뿐, 후보 제외 조건은 아니다.
- 로컬 환경에서는 기존 4명과 생성형 96명을 합친 100명의 `seed` 후보를 자동으로 만든다.
  각 후보는 국가·성별·연령·언어·MBTI·관심사·소개를 가지며, 운영 환경에서는 생성하지 않는다.
- 후보 필터는 1인칭 기준이다. 내 국가·성별·연령 조건만 적용하며, 상대방의 조건은 확인하지 않는다.
  후보 API는 한 요청에 최대 10명을 반환한다. 새 배치를 요청할 때는 미노출 후보를 먼저, 그다음
  가장 오래 전에 노출한 후보를 우선하고 동률은 사용자별 일일 랜덤 순서로 정한다.
- `match_exposures`에 노출·패스 이력을 저장하고 `POST /v1/matches/candidates/{candidate_id}/pass`로
  패스를 기록한다. 패스는 영구 제외가 아니므로 다음 배치에 다시 노출될 수 있다. 좋아요·상호 매칭은 현재 도입하지 않는다. 통화 요청의 상태
  영속화와 signaling은 05. Voice signaling 완성 범위에서 MySQL로 전환한다.
- 유효한 통화 session에 참여 중인 사용자는 후보에서 제외한다. 후보 카드가 표시된 뒤 상대가 다른
  통화를 먼저 시작하면 신청 생성은 `candidate_busy`로 거절하고, 클라이언트는 상대가 통화 중임을 안내한다.

04. Chat MySQL 전환
완료
- 대화, 멤버, 메시지, 읽음 상태를 MySQL repository로 전환했다.
- cursor pagination, 대화방 멤버 권한 검사와 상대 탈퇴 시 대화 삭제 정책을 적용했다.
- 실시간 WebSocket은 추가하지 않고 REST 새로고침 구조를 유지한다. 차단 정책은 06. Safety API에서 추가한다.

05. Voice signaling 완성
완료
- 통화 요청 수락·거절·취소와 연결 전 P2P SDP/ICE signal polling을 MySQL 기반으로 전환했다.
  연결 뒤에는 Data Channel으로 종료를 직접 전달하며, WebRTC 연결 단절 때만 session 상태를 한 번
  확인한다.
- 신청은 15초(5초 발신 전환 화면 + 10초 응답 대기), 연결 session은 30분 뒤 만료 처리하며,
  참여자 권한과 통화 종료를 DB 기준으로 검증한다.
  SDP/ICE signal은 10분 뒤 만료 처리한다. 무료·Plus 모두 한 session당 30분 상한을 적용한다.
  서버는 오디오를 relay하지 않는다.
- P2P 실패 뒤 TURN 도입 여부는 실기기 검증 결과를 보고 결정한다.

06. Notification·Safety API
- Android FCM token 등록/폐기와 통화·새 메시지 전달 코드를 추가했다. Firebase Console Android
  설정과 서버 service-account credential을 넣은 실기기 검증이 남아 있다. iOS APNs 전달은
  Apple Developer 설정 이후 추가한다.
- 매칭 후보는 통화 알림 권한·device token·foreground 상태로 제한하지 않는다. 앱은 로그인·home 진입·
  foreground 복귀·background 전환 때만 단발성 presence를 갱신하며, 서버는 최근 foreground 상태와
  유효한 통화 알림 token을 후보 정렬의 내부 우선순위로만 사용한다. Android FCM 발송 코드는 provider
  credential을 넣으면 동작하며, iOS APNs 발송은 Apple provider 설정 뒤 추가한다.
- 재방문 유도는 별도 후속 작업으로 둔다. 장기간 foreground 신호가 없는 사용자를 후보에서 즉시
  제외하기보다, 3일·7일·14일 경과 시 FCM/APNs를 한 번씩 보내 앱을 열어 `is_foreground=true`를
  다시 보고할 기회를 준다. 알림 미허용 사용자에게는 발송하지 않으며, 재방문 알림 발송 여부는 후보
  자격과 분리한다.
- 차단, 신고, 정책 동의, 성인 확인, 계정 삭제 API와 운영 데이터 보존 정책을 정의한다.
- 온보딩은 프로필 정보 확인 뒤 필수 정책 동의를 받는다. 현재 버전의 이용약관, 개인정보 처리방침,
  커뮤니티 가이드라인, 만 15세 이상 확인은 동의 시각·표시 언어와 함께 MySQL에 이력으로 저장하고,
  이 동의가 완료돼야 `profiles.onboarding_completed`를 true로 전환한다.
- 프로필 사진은 사전 자동 검수·운영자 승인 없이 즉시 노출한다. 신고가 접수된 뒤에만 운영자가
  숨김·삭제·계정 제한 등의 조치를 할 수 있게 한다.
- 사진·프로필·메시지 신고 API를 추가한다. 신고 사유, 대상 스냅샷, 신고 시각, 처리 상태와 운영자
  조치 이력을 보존한다.
- 신고자는 최근 24시간에 최대 5건만 제출할 수 있고, 같은 대상의 최근 24시간 중복 신고는 거절한다.
  서로 다른 신고자 3명 이상이 같은 사용자를 최근 24시간에 신고하면 해당 계정은 24시간 자동 제한한다.
  제한 중에도 로그인·프로필·설정은 가능하지만 매칭·채팅·통화와 availability presence 갱신은 서버에서 차단한다.
  자동 제한 시 pending 통화 요청을 취소하고 진행 중 통화 세션을 종료한다.
- 운영자 페이지는 현재 범위에 넣지 않는다. 추후 운영자는 신고 사유·선택 증거·신고자·피신고자·처리 상태와
  자동 정지 이력을 검색·열람할 수 있어야 하며, 수동 제한/해제·콘텐츠 숨김 조치에는 조치자·사유·시각을 남긴다.
- 출시 전 필수 보완(법률 검토 대상): 현재 앱 안의 정책 전문은 제품 초안이다. 공개용 확정본에는
  사업자명·주소·대표자·지원/개인정보 문의처, 수집 항목별 구체적 이용 목적, 외부 제공자와 국외 이전 여부,
  보관 기간·백업 삭제·로그 보존 기간, 열람·정정·삭제·이용정지 요청 절차, 안전관리 조치 개요를 포함한다.
- Google 인증, private S3 호환 사진 storage, FCM/APNs, 향후 광고·분석 SDK를 실제 도입할 때마다
  개인정보처리방침·스토어 Data Safety 선언·동의 흐름을 함께 갱신한다. 선택적 광고·분석은 필수 약관 동의에
  묶지 않는다.
- UGC(사진·프로필·메시지)가 있는 서비스는 문구만으로 충분하지 않다. 차단·신고 API와 운영 처리 경로,
  공개 문의처, 콘텐츠·계정 제한 기준을 실제로 제공한 뒤에만 해당 기능을 공개한다.
- 만 15세 이상 정책은 단순 체크가 아닌 신뢰 가능한 연령 확인 및 출시 국가별 미성년자 보호 기준으로
  보완한다. 약관에는 사업자의 법적 책임을 전면 면제하는 표현을 사용하지 않으며, 유료 기능 도입 시에는
  가격·환불·해지·전자상거래 고지 요건을 별도로 검토한다.

07. 운영·iOS 출시 준비
- Cloud Run(FastAPI) + Cloud SQL(MySQL) + Cloudflare R2 운영 Terraform과 Cloud Run migration job을
  추가했다. Cloud Run이 HTTPS를 종료하므로 Caddy/공개 VM은 사용하지 않는다. Cloud SQL은 초기
  `db-f1-micro` 단일 영역·HA 미사용으로 시작한다. Secret 원본은 Secret Manager가 기준이며, 운영자
  확인 목적상 dev의 DB URL·JWT·Swagger Basic Auth 네 값만 Cloud Run revision YAML에 평문 환경변수로
  materialize한다. staging/prod는 Secret Manager 참조를 유지한다.
- Swagger/OpenAPI는 `/v1/docs`, `/v1/openapi.json`, `/v1/redoc`으로 제공한다. local은 공개하고,
  dev/staging은 Bootstrap이 생성한 `mohano-admin` Basic Auth를 요구하며, prod에서는 문서 route를
  등록하지 않는다.
- GitHub Actions CI/CD는 badara-server와 같은 WIF(OIDC)를 사용한다. `dev` branch는 dev, `staging`
  branch는 staging, `main` branch는 prod deploy service account만 impersonate한다. 모든 환경 push는
  Bootstrap apply → SHA image build/push → migration job 성공 → API revision 갱신 순서로 자동 실행한다.
  GitHub에는 service-account key JSON·DB/JWT/R2 secret을 저장하지 않는다.
- 실제 Terraform 적용, R2 CORS·lifecycle, production DNS/CORS/OAuth redirect URL, GCS Terraform state
  bucket, GitHub Actions Variables·production 승인,
  billing budget·monitoring과 restore drill은 운영 전 확인한다.
- iOS Google OAuth와 APNs 설정은 macOS/iOS 빌드 환경에서 별도로 검증한다.

08. 광고·구독 수익화
- Google AdMob 등 광고 제공자와 광고 형식(배너·네이티브·보상형)을 확정하고, 개발·운영 ad unit을
  분리한다. 광고 SDK와 표시 UI는 Flutter 앱이 담당한다.
- 통화 요청·연결·종료, 온보딩, 프로필 편집처럼 사용자 흐름과 신뢰가 중요한 화면에는 광고를 표시하지
  않는다. 채팅 목록 또는 매칭 배치 전환을 후보 위치로 검토한다.
- 만 15세 이상 사용자를 전제로 국가별 동의, 미성년자 대상 개인 맞춤 광고 제한, 개인정보처리방침과
  광고 식별자 동의·철회 정책을 확정한다.
- 서버는 광고 제공자의 비밀키·광고 식별자를 클라이언트에 대리 전달하지 않는다. 광고 노출·클릭을
  측정해야 할 경우 개인정보가 없는 집계 이벤트 계약과 보존 기간을 별도로 정의한다.
- 무료 이용자는 후보 10명 배치를 모두 확인한 뒤 다음 10명을 다시 검색할 때 전면광고 1회를 본다.
  해당 배치에서 통화가 성사됐는지와 무관하게, 다음 배치 요청에는 같은 규칙을 적용한다.
- 무료 이용자는 상대별로 그날의 첫 메시지를 보내기 전에 전면광고 1회를 표시한다. 이후 같은 상대에게
  보낸 무료 메시지 10건마다 다음 광고 gate를 적용하고, 앱에는 다음 광고까지의 당일 무료 메시지 수를
  `n/10`으로 표시한다. 날짜가 바뀌면 같은 상대와의 첫 메시지에도 다시 광고를 적용한다.
- 무료·월 780엔 자동 갱신 구독자 모두 한 session당 최대 30분으로 제한한다. Plus는 광고 없이
  통화 횟수·채팅을 이용하는 상품이며, 통화 시간 상한은 안전·비용 기준으로 유지한다.
- 구독 entitlement는 Google Play Billing·App Store StoreKit의 구매 결과만 신뢰해 서버에서 검증·보관하며,
  복원, 취소·환불·만료·결제 유예 상태와 기기 간 entitlement 동기화를 구현한다.
- 광고 재고 없음·네트워크 오류로 광고를 표시하지 못했을 때 사용자를 무기한 막지 않는 fallback,
  광고 시청 상태의 서버 영속화/중복 방지, 30분 종료 전 경고와 유료 이용자의 기술적 안전 상한을
  별도로 결정한다.
- 강제 외부 광고는 후보 10명 배치 전환과 상대별 메시지 광고 gate 두 지점으로 한정한다. 대신 당일
  두 번째 광고 gate부터는 `광고 없이 계속하기 — 월 780엔`처럼 자체 구독 플랜을 조용히 제안한다.
  앱 기동·온보딩·프로필 편집·사진 업로드·채팅 목록·통화·신고/차단/설정에는 외부 광고를 넣지 않는다.
- migration `20261120_0013`은 구독 entitlement와 후보·채팅의 현지 날짜별 광고 gate 기록을 만든다.
  실제 AdMob 연결 전 개발 단계에서는 서버가 gate를 판정하고 앱의 개발 미리보기 완료 동작으로만
  해제한다. production 광고 노출·구매로 취급하지 않는다.

현재 구현 범위
--------------
- `GET /v1/health`
- 익명 사용자 생성, Google·Apple ID token 교환, access/refresh JWT 발급·갱신·로그아웃
- 내 프로필·사진 참조값, 매칭 조건·후보, 통화 신청·signaling, REST 채팅·읽음 API
- 인증 사용자·Google/Apple identity·refresh session·프로필·매칭·채팅·통화 signaling은 MySQL에 영속화한다.
- Alembic migration은 users, auth_identities, refresh_sessions와 프로필·매칭 조건·통화
  신청·P2P signal·대화·메시지 테이블까지 정의한다. 채팅과 통화 API는 MySQL repository를 사용한다.

구조 원칙
---------
- `app/api/v1`은 Spring Boot의 Controller에 해당하며 요청 검증, 인증 의존성, 응답만 맡는다.
- `app/services`는 기능별 클래스의 business/service 계층이며, 정책·권한·상태 전이를 담당한다.
- `MockStore`는 임시 repository 역할이다. MySQL 전환 때에는 router가 아니라 service의 저장소
  의존성만 실제 repository로 교체한다.
